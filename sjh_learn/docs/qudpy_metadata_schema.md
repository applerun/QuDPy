# QuDPy Metadata Schema Specification

Version: 0.1  
Status: baseline schema  
Scope: `meta.json` and `debug_meta.json` generated by `save_result_case()` for `DynamicsResult`

## 1. Design goal

QuDPy metadata is split into two layers:

- `meta.json`: compact, human-readable, physical-unit-first summary of one simulation result.
- `debug_meta.json`: verbose internal diagnostic record for debugging, reproducibility, code-unit conversion, solver adapters, and sanity-check details.

The default metadata schema must support both two-level and general N-level systems. It must not assume that a system has only one transition, one energy gap, one detuning, one Rabi frequency, or one dephasing rate.

## 2. Top-level schema

For `meta.json`, the top-level structure should remain:

```text
result_type
example_name
condition_name
case_name
mode
source_mode
user_input
system
field
dissipation
time_grid
solver
trajectory_summary
sanity_summary
component_export
output_files
```

No other top-level blocks should be added unless they describe a genuinely new conceptual layer.

Deprecated top-level blocks for `meta.json`:

```text
inputs_physical
input_field
input_field_rebuild
derived_physical
solver_representation
lab_frame_solver
rotating_transform
input_drive
solver_code_summary
```

If information from these old blocks is still needed, move it into one of the approved blocks above or into `debug_meta.json`.

## 3. `user_input`

Purpose: preserve the user-provided description and optional user metadata.

Allowed structure:

```json
"user_input": {
  "description": "...",
  "metadata": {
    "...": "..."
  }
}
```

Rules:

- This block may contain user-supplied notes such as `transitions_eV` or `dipoles_D`.
- These user-supplied notes are not the canonical machine-readable system description.
- Canonical system information must live in `system`.
- Do not copy `user_input.metadata` into `field`, field adapters, or field rebuild metadata.

## 4. `system`

Purpose: describe the quantum matter system.

Required fields:

```text
basis
dimension
energies_eV
dipole_matrix_D
transition_table
```

Recommended structure:

```json
"system": {
  "basis": ["0", "1", "2"],
  "dimension": 3,
  "energies_eV": [0.0, 1.5, 1.75],
  "dipole_matrix_D": [[...]],
  "transition_table_rule": "all i < j transitions; dipole_coupled indicates nonzero dipole",
  "transition_table": [...]
}
```

### 4.1 Energies

`energies_eV` is the canonical energy-level list in physical units.

For an N-level system, transition energies should be derived from:

```text
transition_energy_eV(i, j) = energies_eV[j] - energies_eV[i], for i < j
```

### 4.2 Dipole matrix

`dipole_matrix_D` is the canonical matter-light coupling matrix in Debye.

Rules:

- This belongs in `system`, not `field`.
- Store it as a full matrix.
- If complex dipoles are supported, entries should be JSON-safe complex records: `{"real": ..., "imag": ...}`.

### 4.3 Transition table

`transition_table` should be automatically generated from `energies_eV`, `dipole_matrix_D`, `laser_energy_eV`, and solver-derived coupling values.

Each row should have:

```json
{
  "from": 0,
  "to": 1,
  "label": "0_to_1",
  "energy_eV": 1.5,
  "omega_fs_inv": 2.278901173214266,
  "laser_energy_eV": 1.625,
  "detuning_eV": -0.125,
  "detuning_fs_inv": -0.18990843110118893,
  "dipole_D": {"real": 3.0, "imag": 0.0},
  "coupling_fs_inv": {"real": 0.0009489083473202662, "imag": 0.0},
  "dipole_coupled": true
}
```

Rules:

- By default, include all upper-triangular pairs `i < j`.
- Use `dipole_coupled = false` when the dipole is zero or below tolerance.
- Do not remove dark transitions unless an explicit filtering option is added.
- If all transitions are included, include `transition_table_rule`.

### 4.4 Two-level compatibility fields

For `dimension == 2`, `system` may additionally include:

```text
energy_gap_eV
detuning_eV
```

Rules:

- These are compatibility convenience fields only.
- They are allowed only for `dimension == 2`.
- For `dimension > 2`, these singular fields must not be written.

## 5. `field`

Purpose: describe the optical input field only.

Allowed structure:

```json
"field": {
  "class": "GaussianCarrierFieldPhysical",
  "expression": "E(t) = 2 E0 f(t) cos(omega_L t + phase)",
  "parameters": {
    "E0_MV_per_cm": 0.1,
    "peak_E_MV_per_cm": 0.2,
    "omega_L_fs_inv": 2.468809604315455,
    "laser_energy_eV": 1.625,
    "phase_rad": 0.0,
    "envelope": "gaussian",
    "pulse_center_fs": 0.0,
    "pulse_sigma_fs": 5.0
  },
  "units": {
    "field": "MV/cm",
    "time": "fs"
  },
  "amplitude_convention": "field_MV_per_cm is E0 in E(t) = 2 E0 f(t) cos(omega_L t + phase).",
  "rebuildable": true,
  "debug_details": "debug_meta.json"
}
```

Rules:

- `field` must not contain `dipole_matrix_D`, `dipoles_D`, `transitions_eV`, `transition_table`, relaxation channels, or pure dephasing channels.
- `field` must not copy `user_input.metadata`.
- Full rebuild internals may go into `debug_meta.json`.

## 6. `dissipation`

Purpose: describe relaxation and pure dephasing channels in physical units.

Recommended structure:

```json
"dissipation": {
  "relaxation_channels": [
    {
      "name": "relaxation_1_to_0",
      "from_level": 1,
      "to_level": 0,
      "T1_fs": 800.0,
      "rate_fs_inv": 0.00125
    }
  ],
  "pure_dephasing_channels": [
    {
      "name": "pure_dephasing_level_1",
      "level": 1,
      "Tphi_fs": 250.0,
      "rate_fs_inv": 0.004
    }
  ]
}
```

Rules:

- Use physical units.
- Do not store code-unit rates in `meta.json`.
- Code-unit rates belong in `debug_meta.json`.

## 7. `time_grid`

Purpose: describe the simulation time axis in physical units.

Recommended structure:

```json
"time_grid": {
  "t_start_fs": -1000.0,
  "t_end_fs": 1000.0,
  "dt_fs": 0.05,
  "n_time_points": 40001,
  "time_axis_unit": "fs"
}
```

Rules:

- Prefer physical time in `fs`.
- Code-unit time grid belongs in `debug_meta.json`.
- Full time arrays should not be duplicated in JSON metadata.

## 8. `solver`

Purpose: describe the simulation representation and solver semantics.

Recommended structure for `lab_exact`:

```json
"solver": {
  "mode": "lab_exact",
  "description": "Direct lab-frame propagation with the full time-dependent optical carrier.",
  "hamiltonian_type": "time-dependent lab-frame Hamiltonian",
  "uses_lab_field_directly": true,
  "uses_rwa_drive": false,
  "uses_rotating_transform": false,
  "carrier_retained": true,
  "counter_rotating_terms_retained": true,
  "rwa_approximation_applied": false,
  "independently_solved_by_mesolve": true,
  "interaction": "H_int(t) = -mu E(t)"
}
```

Rules:

- Merge old `solver_representation` and `lab_frame_solver` semantics here.
- For `lab_exact`, do not write a separate `input_drive` block.
- For `rwa`, RWA-specific drive details may be stored here or in a mode-specific subsection, but should not reintroduce obsolete top-level `input_drive`.

## 9. `trajectory_summary`

Purpose: compact summary of the simulated density matrix trajectory.

Recommended fields:

```text
n_time_points
time_range_fs
dimension
final_populations
max_populations
final_coherences
max_trace_error
max_hermiticity_error
```

Rules:

- Include all populations.
- Include upper-triangular off-diagonal coherences.
- Coherence summary may include `final_abs`, `max_abs`, `final_phase`, and `final_phase_unwrapped`.
- Large arrays do not belong here.

## 10. `sanity_summary`

Purpose: expose important numerical sanity-check results in `meta.json`.

Recommended structure:

```json
"sanity_summary": {
  "trace_error_small": true,
  "hermiticity_error_small": false,
  "max_trace_error": 2.22e-16,
  "max_hermiticity_error": 2.28e-7,
  "details": "debug_meta.json"
}
```

Rules:

- Keep this compact.
- Full sanity-check details belong in `debug_meta.json`.
- Failed sanity checks should be visible from `meta.json`.

## 11. `component_export`

Purpose: describe what density matrix components are saved.

Recommended structure:

```json
"component_export": {
  "dimension": 3,
  "component_indexing": "zero_based",
  "saved_populations": ["rho_00", "rho_11", "rho_22"],
  "saved_coherences": ["rho_01", "rho_02", "rho_12"],
  "saved_coherences_rule": "upper triangular off-diagonal elements only",
  "coherence_components": ["real", "imag", "abs", "phase", "phase_unwrapped"],
  "saved_observables": [],
  "observable_note": "Observable, polarization, FFT, and absorption-like quantities are analysis-layer outputs.",
  "density_npz": "full density matrix trajectory"
}
```

Rules:

- This block describes exported density-matrix components, not physical spectroscopy post-processing.
- If spectra or polarization outputs are added later, describe them separately.

## 12. `output_files`

Purpose: list files generated for this case.

Recommended structure:

```json
"output_files": {
  "density": "data/density.npz",
  "components": "data/components.csv",
  "populations": "data/populations.csv",
  "preview": "figs/preview.png",
  "debug_metadata": "debug_meta.json",
  "component_figures": {
    "rho_01": "figs/component/rho_01.png",
    "rho_02": "figs/component/rho_02.png",
    "rho_12": "figs/component/rho_12.png"
  },
  "component_figures_dir": "figs/component"
}
```

Rules:

- `component_figures` should include all generated component figures.
- `component_figures_dir` should be written if component figures exist.
- Paths should be relative to the case directory.

## 13. `debug_meta.json`

Purpose: verbose internal record for debugging and reproducibility.

Allowed content:

```text
summary
sanity_checks
result_metadata
drive_dict
parameters_code
physical_params
solver_params_fs_inv
solver_params_code
example_name
condition_name
case_name
```

Rules:

- `debug_meta.json` may include code-unit quantities.
- It may include adapter internals.
- It may include full solver parameters.
- It should not duplicate full time arrays; use summaries.
- Field adapter metadata should not contain matter-system metadata such as `dipoles_D` or `transitions_eV`.
- `source_field.metadata.user_metadata` should not be written.
- If user input metadata is needed, it belongs in `physical_params.input_metadata` or top-level user-input records, not inside field adapters.

## 14. Explicit non-goals

The metadata schema should not:

- Change solver numerical behavior.
- Change Hamiltonian construction.
- Change Lindblad channel construction.
- Change spectroscopy post-processing.
- Change plotting style.
- Treat N-level systems as implicit two-level systems.
- Use one global `energy_gap_eV`, `detuning_eV`, `rabi_fs_inv`, or `gamma2_fs_inv` for `dimension > 2`.

## 15. Regression checks

Recommended metadata regression checks:

### 15.1 Compact top-level schema

For `meta.json`, verify top-level keys are exactly or at least restricted to:

```text
result_type
example_name
condition_name
case_name
mode
source_mode
user_input
system
field
dissipation
time_grid
solver
trajectory_summary
sanity_summary
component_export
output_files
```

### 15.2 Field block cleanliness

Verify `field` does not contain:

```text
dipoles_D
dipole_matrix_D
transitions_eV
transition_table
user_metadata
relaxation_channels
pure_dephasing_channels
```

### 15.3 Multilevel singular-field exclusion

For `dimension > 2`, verify `system` does not contain:

```text
energy_gap_eV
detuning_eV
```

Verify `meta.json` does not contain obsolete top-level `derived_physical`.

### 15.4 Two-level compatibility

For `dimension == 2`, verify:

```text
system.energy_gap_eV exists
system.detuning_eV exists
system.transition_table exists
len(system.transition_table) == 1
```

### 15.5 Multilevel transition table

For `dimension == N`, verify:

```text
len(system.transition_table) == N * (N - 1) / 2
```

unless an explicit filter is applied.

### 15.6 Component figure output files

If component figures are generated, verify:

```text
output_files.component_figures exists
output_files.component_figures_dir exists
```

### 15.7 Sanity summary

Verify `sanity_summary` exposes:

```text
trace_error_small
hermiticity_error_small
max_trace_error
max_hermiticity_error
details
```
